Make the source definition the parser

A connector only decodes a transport class. A versioned, user-authored mapping parses each provider response into a stable data contract. Neither the agent nor the dashboard ever inspects provider JSON.

Ingestion contract Documented 2026-07-23 Ingestion → agent → dashboard
Core rule Config-driven must mean a mapping the frontend can author — not a developer writing YAML by hand. The product boundary is a mapping compiler, preview API, and versioned database model.

Runtime path for every fetch

1

Connector

HTTP, iCal, RSS, or HTML fetch plus transport decoding. Produces raw records; knows no Athena semantics.

→
2

Source mapping

Select record root, extract fields, apply safe transforms, compute identity. This is where a new API response is parsed.

→
3

Data contract

Validate normalized fields against a versioned semantic schema such as task, event, scalar, or generic record.

→
4

Result store

Upsert the stable envelope and retain provenance. Notify consumers that the source revision changed.

Connector decodes JSON syntax · mapping interprets the provider shape · contract validation guarantees the downstream shape.

What the frontend “Add source” form creates

1Connect

URL, method, parameters, authentication reference, schedule, and connector type.

2Sample

Backend performs a test fetch and returns a redacted response tree plus candidate record arrays.

3Map

User picks the record root and maps response fields to an existing schema; suggestions may be automatic.

4Validate and preview

Show normalized rows, computed IDs, agent context, and dashboard rendering before activation.

5Save version

Persist source definition, mapping version, schema reference, and encrypted credential reference.

6Activate

Only a passing definition is scheduled. Later edits create a draft and preserve the last working version.

Stable result contract

Keep arbitrary normalized data, but promote a small set of cross-source fields into facets so agent and dashboard can query without understanding every payload.

SectionContentsWhy it exists
identity source_id, record_id, schema_id, schema_version Stable deduplication and schema lookup
data Normalized domain fields The only source-specific values that reach consumers
time observed_at, effective_at, expires_at Freshness, planning windows, and stale-state handling
facets title, status, priority, start_at, end_at, url Common filtering without understanding every payload
provenance fetch_run_id, source_url, content_hash Auditability and links back to the origin

How consumers connect

Agent context service Read model
  • Queries results by schema, facets, freshness, and planning window.
  • Returns structured normalized entities plus schema descriptions — not preformatted provider strings.
  • Builds the planning snapshot on demand and records which result revision the plan used.
Dashboard API Read model
  • Uses the same query service and result revisions as the agent.
  • Renders known schemas with reusable widgets; unknown schemas with schema-driven table/card layouts.
  • Reads source health and mapping errors separately from result data.
Integration rule Ingestion writes results; agent and dashboard read through one result query/projection service. A change revision can mark a cached plan stale, but ingestion does not invoke the planning agent on every poll.

When adding a source requires code

ChangeCode?Action
New JSON API response shape No Create a mapping in the onboarding UI
New source using an existing schema No Reuse schema; map provider fields into it
New domain shape Usually no Create a data schema and use generic dashboard rendering
New transport or document format Yes, once Add a connector/decoder such as iCal or HTML
New transform not expressible in the mapping DSL Yes, once Add a safe reusable transform operation
Highly interactive or stateful site Yes Add a specialized connector; do not hide code in config

Recommended delivery order

1. Contract first

Define SourceDefinition, MappingDefinition, DataSchema, and ResultRecord. Add fixtures and mapping tests.

2. Onboarding API

Implement test fetch, response-tree inspection, mapping preview, validation, versioning, and activation.

3. Consumers

Add one result query service, agent context builder, generic dashboard renderer, and stale-plan revision tracking.
